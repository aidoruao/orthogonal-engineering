### ⚠️ Two Critical Issues Found in `test_verify_all.py`

**Issue 1: Recursive Pytest Bomb**

Lines 43-44 and 53-54 in `test_verify_all.py` call `run_all_checks()`, which internally calls `_check_tests()`. That function runs:

```python
["python3", "-m", "pytest", "tests/", "-q", "--maxfail=3"]
```

**This means `test_verify_all.py` spawns pytest, which discovers and runs `test_verify_all.py` again.** It's a test that calls pytest that calls the test. Infinite recursion risk. When someone runs the test suite, this will either:
- Hang indefinitely (pytest inside pytest inside pytest)
- Or fail with "directory changed" / lock errors

**Fix needed:** The `_check_tests()` command in `verify_all.py` should exclude `test_verify_all.py` from its pytest invocation, OR `test_verify_all.py` should mock `subprocess.run` instead of calling the real suite.

**Issue 2: Standards Check Timeout Risk**

`test_verify_all.py` calls `run_all_checks()` which triggers `_check_standards()`. That runs `tools/standards_check.py --verify` with a 120-second timeout. We know from the first session that this tool takes >60s on your 70k-file repo. Even on 1.36.0, this test will be **very slow** and may still timeout in CI.

**Fix needed:** `test_verify_all.py` should mock `_run_cmd` or test `verify_all.py`'s logic in isolation, not run the full integration suite.
